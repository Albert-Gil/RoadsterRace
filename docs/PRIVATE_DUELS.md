# Private Duels beta

Multiplayer offers a same-device race and a private room. In a room, two to four human drivers each use one device. The host selects Newport Island, Golden Gate or Santa Monica and one to six laps (San Diego Fleet too when the server sets `DUEL_EXTRA_VENUES=san-diego-fleet`: `/health` lists the enabled venues and the app offers only those; the flag stays off until the real-device four-player test passes), and can change both in the lobby and on the results screen; a different circuit after a race means everyone draws new lines. Once drawing has lasted 90 seconds, the host can remove a driver who has not locked a line; that driver gets no reconnect window and the others race. Open the invite or enter its code, draw privately, then lock in. The shared countdown begins once every driver has a valid line. The race menu leaves the shared clock running. Results show the same standings to everyone. Remaining drivers vote Race again or New lines; once everyone still connected has voted, any New lines vote starts a fresh drawing round (the same rule as same-device play, `src/core/rematch-vote.ts`). Votes can change until then. Online races do not award local medals, records or challenge stamps.

Each device chooses its own driver name and available paint before creating or joining a room, including through an invite. These choices persist in that device's driver preferences. Reloading an existing seat reconnects directly with its original room identity. Both multiplayer modes show only the current driver's line during drawing and preview and hide every line once planning is complete. The server sends each seat only its own stroke.

## Run locally

Use Node 24 and the pinned pnpm. Install with `pnpm install --frozen-lockfile`. Run `pnpm duel:build`, then `pnpm duel:serve` in one terminal and `pnpm dev --host 0.0.0.0` in another. Development clients use port 2567 on the device hosting the game. For a different address, set `VITE_DUEL_SERVER` to the room service's HTTPS origin before starting Vite or building. Keep the website and room service independently deployable.

## Internet test

1. Deploy the repository's Render Blueprint (`render.yaml`) to a free Oregon web service. The health endpoint is `/health`. Keep the service on free compute for this beta.
2. Set the GitHub Actions repository **variable** `ROADSTER_DUEL_SERVER` to the assigned public HTTPS origin. The existing verified Pages workflow embeds it when building the site. Use the assigned origin even if Render appends a suffix to the service name. No Render credentials belong in the game or its repository.
3. Copy the room service's Deploy Hook URL from Render Settings to the GitHub Actions secret `RENDER_DEPLOY_HOOK_URL` in the `github-pages` environment. Render's independent auto-deploy is off. The server build writes `dist-server/contract.json`: a hash of every source module in the server bundle plus the lockfile (`server/contract.ts`). `/health` reports that contract with the protocol, physics, compiler and track versions. After verification, the Pages workflow builds the same contract and calls Render only when the live contract differs, then waits for `/health` to report it before publishing. Website-only releases therefore keep live rooms. A superseded commit publishes nothing (the newer run does). Without `ROADSTER_DUEL_SERVER` the build hides Private Duels and the website publishes alone. With it, a live server that is outdated or cannot be verified is deployed through the hook first; if the hook secret is missing or invalid, the release **holds** (the workflow fails and Pages is not published) rather than shipping a game the live server cannot serve. If a requested server update never becomes healthy, the website also waits for a successful retry (`tools/duel-release.ts`). After publishing, the `public-smoke` job opens the public site in a fresh browser, waits for the released build (`<html data-build>`), creates a Newport Island room, joins it from a second browser and leaves; a failure fails the run (`tools/public-smoke.mjs`; run it by hand with `node tools/public-smoke.mjs --url <site>`). Revert and release from `main` to roll back both services together.
4. Check the first join after idle, an active two-device race and a reconnect from cellular. A sleeping free instance may take about a minute to start. A process restart closes its rooms. One free instance stores sessions in memory, without accounts or a database.

## Enabling San Diego Fleet

Fleet duels are built, tested in CI (`tests/unit/private-duels.test.ts`, `tests/duels/fleet.spec.ts`) and hidden until the room server sets `DUEL_EXTRA_VENUES=san-diego-fleet`. Enable it only after a real-device test passes:

1. Steps 1–3 above are done and `/health` reports the current contract.
2. In Render, add `DUEL_EXTRA_VENUES=san-diego-fleet` temporarily (Render restarts the service; live rooms close). `/health` must list `san-diego-fleet` under `venues`.
3. Four real devices, at least one iPhone in Safari on cellular (Wi-Fi off) and one in portrait: create a Fleet room, 1 lap; everyone joins from the shared invite.
4. Draw: one main route, one route through each support-ship shortcut, one deliberately slow line. Lock in. Check each preview shows the amber ramp rings for a slow line, and nobody sees anyone else's line.
5. Mid-drawing, lock and unlock the iPhone, or switch it to another app for 10 s, then return: the drawing board comes back.
6. Race: press Hop at a support-ship lip. Watch flights and a missed landing on another phone: the car rises and lands on the decks, and a missed landing recovers once, without flicker or a car hanging in the air.
7. Results show the same standings and times on every device. Vote **Race again**, finish a second race, then **New lines**: everyone draws fresh with no old lines shown.
8. Note any failure with the device, network, step and room code. If all pass, keep the variable; otherwise remove it (Fleet disappears from the pickers on the next app open).



The Colyseus server runs one existing LocalRace per room at 60 Hz. Clients submit the combined sector stroke once, in metres and elapsed milliseconds. The server uses the ordinary route compiler including off-road hazards. Other drivers receive readiness only. All four cars are rendered from shared 20 Hz reports. Other cars are drawn 100 ms behind the server, interpolated and snapped across recovery. Your own car is drawn where the room will be when a press sent now arrives: the newest server pose moved along your own line by the frame's age plus twice the measured one-way delay (from command round trips), at most 200 ms ahead. The car is located within its current section of the line (never a neighbouring deck) unless a point elsewhere on the line is clearly closer (more than 4 m), the lead stops at each takeoff lip until the room reports the flight, the flight itself is drawn from the newest authoritative pose, and recovery and the finish fall back to the buffer. Switching between these, or a lead that shrinks, closes the gap over 1.5x the time needed to cover it, so the car slows rather than stopping or stepping backwards; a target that stays behind for 0.6 s is taken as it is (`src/duels/own-car.ts`). Each measured press in the latency spec reports the display state (mode, catching up, route distances, lead). Input feedback is local, and the server decides whether a Hop or Thrust actually fires.

Protocol 4 is defined in `src/duels/protocol.ts` (frames as in protocol 2; protocol 3 changed room codes to words; protocol 4 added private ability results, typed errors, word-and-digit codes and invite stamps). Each car in a frame is a flat array of integers (`carCodec`): positions and elevation in centimetres, angles in milliradians, times in milliseconds, booleans as 0/1 and enums as indexes. Thrust and Hop readiness are not broadcast; each seat receives its own through a `cooldowns` message when it changes. Protocol 2 frames are about 3x smaller than protocol 1 (330 kB instead of 1.0 MB per player-minute in the benchmark). A Thrust or Hop pressed in the last countdown beat is held by the client and sent with the first racing frame; a press the server has not confirmed within 0.6 s shows a "missed" notice. X/Z are horizontal metres, elevation is metres upward, positive heading rotates clockwise from +Z in radians. One tick is 1/60 second. The host chooses room settings only. Each driver has a seat ID and a separate SDK reconnection credential, stored in the joining tab's session storage. The room code is one everyday English word and a digit from 2–9, such as TIGER7 (256 × 8 codes; `src/duels/codes.ts`), typed in any case; it is shareable and cannot reclaim a seat. Invite links also carry the room's creation stamp (`&since=`), so a link made for an earlier room that reused the code says the invite has expired; a typed code joins normally. Ten failed joins a minute from one address are refused for a minute (`server/join-limiter.ts`). Plain-word, six-character and 9–10-character codes from earlier releases say the invite is outdated. The lobby offers **Share invite** (the system share sheet, where available) and **Copy link**. An invite in the old 10-character format explains that it is outdated. When the Private Duel screen opens, and again before joining, the client compares `/health` versions with its own (a server that reports no protocol at all counts as outdated). If either side is ahead, the screen shows **Online play is updating**: Create and Join stay disabled, the invite and saved seat are kept, and `/health` is rechecked every 3 s for up to 15 s (`src/duels/compatibility.ts`). Then it offers **Reload game** when a newer website build is deployed, otherwise **Try again**. It never reloads during drawing or racing. A sleeping server, an unreachable server and an expired room or seat keep their own messages. A rejected reconnection clears the stored seat and says the seat expired; a saved seat that could not be reclaimed at startup shows **Rejoin race**.

| Message | Meaning |
|---|---|
| Join/create options | Protocol, physics/compiler versions, supported track versions, name, paint and, from an invite link, `since` (the room's creation stamp). A version mismatch fails with `version-mismatch`; a stamp for an earlier room fails with `invite-expired`. |
| room | Round number, lobby/drawing/countdown/racing/results phase, circuit/version, laps, host, seats with connection, readiness, withdrawal and vote, and `created` (seconds). |
| start / line | The host locks the lobby. Each seat submits its own round number and ordered [x, z, timeMs] samples. |
| ability | Round, increasing per-seat sequence, most recent observed simulation tick and ability. Commands from another round are dropped. Valid input takes effect on the next legal simulation step. |
| ability-result | To the sending seat only: `{round, sequence, ability, outcome, tick}`. `fired`, `recharging` and `unavailable` are decided at the fixed step that applies the rules; `too-late` (outside the 60-tick window, or not racing) and `duplicate` (an old sequence, or that ability already queued) on receipt. Hop and Thrust pressed together get one reply each. Players see only the usual button and recharge feedback; outcomes, unconfirmed commands (no reply in 1.5 s) and the display error at each press live in development diagnostics (`window.__roadsterDuel.commandLog`). |
| error | To one seat: `{category, reason, detail?}` with category `drawing` (back to your retained line), `lobby` (stays in the lobby or on Results) or `connection`, and a stable reason code from `src/duels/errors.ts`. Create/join failures use the same codes in their ServerError message; the client never shows raw SDK text. |
| frame | Round, authoritative tick, countdown ticks remaining, car rows in `carCodec` order, standings as [player, rank, progress cm, finished, finish ms] and events since the previous broadcast. |
| cooldowns | To one seat only: its round, hopReadyAt and thrustReadyAt (s), sent when they change and on sync. |
| sync / ownLine | After joining or reconnecting, request the current view, latest frame and only that seat's accepted line and last accepted input sequence. |
| rematch | Vote for same or redraw in the current results round. The next round gets a new identity, grid and cooldowns. |

A dropped connection has 30 seconds to reclaim its seat. Its car follows the locked line without new inputs. A withdrawn, unfinished racer receives DNF and leaves contact. A finished driver keeps their finishing time. Local play runs without a room service.

When a driver reloads an invite, the saved credential reclaims the seat before the browser starts the 3D circuit. Once the scene is ready it requests the current round, the driver's own line and the latest standings, including a result reached during loading. Choosing Home explicitly releases the seat and clears its credential.

The transport pings every ten seconds and tolerates six unanswered pings. This lets a connected browser finish a slow graphics upload. A silent network loss can therefore take about a minute to detect. Once the socket closes, the room gives the driver its usual 30 seconds to reconnect.

A future Unity client can use the Colyseus C# SDK to consume the same messages. `tests/fixtures/duel-reference.json` contains actual timestamped lines, command ticks, car checkpoints, contacts, flight/recovery events and finishing order. The three reference races are renderer independent. Run `pnpm exec vitest run tests/unit/duel-reference.test.ts` to check them, and regenerate deliberately with `node --experimental-transform-types tools/duel-references.mjs` when the contract or physics changes.

## Verification and capacity

Run `pnpm typecheck`, `pnpm test`, `pnpm test:legacy`, `pnpm build` and `pnpm duel:build`. Run `pnpm exec playwright test --config playwright.duels.config.ts` for independent browser sessions, mouse/touch drawing and reconnect/rematch. For Pages smoke, build with `VITE_BASE_PATH=/RoadsterRace/` and run `pnpm test:pages`.

`node --experimental-transform-types tools/benchmark-private-duels.mjs` measures simulation/serialization time and uncompressed snapshot payload per player-minute. It excludes TLS, WebSocket overhead, joins and drawings. On the development PC, four simultaneous four-car races used a median 3.25 ms per simulation step (95th percentile 4.97 ms); protocol 2 sends about 0.33 MB of snapshots per player per minute (protocol 1: 1.00 MB). At sixteen rooms the 95th percentile reached 18.44 ms, beyond the 16.67 ms step budget. Because Render Free provides 0.1 CPU, a process admits at most two rooms (`DUEL_MAX_ROOMS`, default 2) and their summed circuit weight must fit `DUEL_CAPACITY` (`server/capacity.ts`). A circuit's weight is its 4-car step time relative to Newport Island, measured on the development CPU until the live numbers replace it (`DUEL_WEIGHTS="lax=12,capitan-yosemite=10"`). The default budget (9.2) admits two rooms of any circuit offered before weights existed; it is the heavy circuits (Snowy Tahoe 8.9, Capitan Yosemite 9.6, LAX 11.2) that it limits. An idle process always admits one room. A host switching an open room to a circuit that no longer fits sees "too busy for that circuit" and keeps the current one.

`/stats` (no secrets, CORS open) reports uptime, `readyMs` (process start to listening, which includes a cold start), rooms by circuit, step median/95th percentile/maximum per circuit for the current minute and the last hour, and the time rooms fell behind real time. Each minute the server also logs one `duel-steps` JSON line per circuit. The release smoke check prints `/stats` in its log and job summary. Read it on the free service before raising a limit or enabling a heavy circuit with `DUEL_EXTRA_VENUES`. Opening the Multiplayer menu sends one background `/health` request (at most once a minute), so a sleeping server starts waking before Private Duel is chosen. The public menu shows Private Duel once its server origin is configured. Physical iPhone Safari, cellular handoff and iPad play require separate hardware verification.
